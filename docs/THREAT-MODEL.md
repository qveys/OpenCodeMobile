# Threat Model — OpenCode Mobile

Status: initial draft (v0.1) — pre-code, based on the fixed product/architecture spec in `BOOTSTRAP.md`. No `docs/ARCHITECTURE.md` or codebase exists yet (tracked by OPE-5 and OPE-4/OPE-9). This document must be revisited once those land, and per policy is reviewed again on every change touching network, authentication, or permissions.

Owner: Security Engineer. Methodology: STRIDE.

## 1. System overview

OpenCode Mobile is a native mobile **remote control** (Android + iOS, Kotlin Multiplatform / Compose Multiplatform) for a **self-hosted** OpenCode Server v2 instance that the user already runs on their own machine (reached over LAN or Tailscale). It is explicitly **not**: an IDE, a local LLM runtime, a cloud backend/proxy, or a reimplementation of OpenCode. There is **no product backend** and **no code/prompt telemetry** — the OpenCode Server is the sole source of truth.

Core capabilities: start/resume agent sessions, watch agent work in real time, approve/deny tool-call permission requests, answer agent questions, dictate prompts (speech-to-text), and review files/diffs.

Planned components (per `BOOTSTRAP.md`, decisions are fixed unless marked "open decision"):

- **UI layer** — Compose Multiplatform, unidirectional data flow, Koin DI, Coroutines/StateFlow.
- **OpenCodeV2Adapter / OpenCodeGateway port** — isolates a generated OpenAPI client from the rest of the app (Clean Architecture boundary).
- **EventProcessor** — one per connection; SSE with mandatory polling fallback, exponential backoff, snapshot + reconciliation on reconnect, **never** auto-replays mutations.
- **Local cache** — disposable SQLDelight store; offline mode is read-only.
- **Platform layer (`expect`/`actual`)** — Keychain/Keystore, biometrics, notifications, speech-to-text.
- **CI/CD** — GitHub Actions: architecture/dependency-rule tests, unit/integration tests, contract tests against a real OpenCode instance and a deterministic `MockOpenCodeServer`; automated release to TestFlight and Google Play (build signing).
- **Distribution** — public open-source repo (MIT), solo maintainer, mandatory PR + review workflow, no direct commits to `main`.

Open product decisions that materially affect risk (flagged throughout): Liquid Glass vs. pure Compose on iOS; single vs. multiple stored server profiles. (The server-profile *import* mechanism itself — deep link/QR — is now specified; see `docs/ARCHITECTURE.md` and T8. Local cache encryption is now resolved; see `docs/ARCHITECTURE.md` and T3. Permission approval from a push notification is now resolved — notifications never carry an inline approve action; see `docs/ARCHITECTURE.md` §"Permission approval confirmation (foreground + authenticated)" and T2.)

## 2. Trust boundaries

| # | Boundary | Notes |
|---|---|---|
| B1 | User device ↔ OpenCode Server | Crosses LAN or a Tailscale tailnet. The server is user-owned but the app currently has no described mechanism to verify it's talking to *the* server vs. an impersonator on the same network. |
| B2 | App process ↔ OS secure storage (Keychain/Keystore, biometrics) | Trusted platform APIs; app must not weaken them (e.g., no plaintext fallback). |
| B3 | App process ↔ OS speech-to-text service | May cross to a third-party cloud (Apple/Google) depending on OS/locale — this can silently violate the "no telemetry" product promise. |
| B4 | App process ↔ OS notification system | Notification actions can be triggered without the app being foregrounded/unlocked; overlay/tapjacking risk on Android. |
| B5 | Local device storage ↔ physical attacker / malware | Device loss, theft, unlocked-device access, OS-level backups (iCloud/Android backup) of the SQLDelight cache. |
| B6 | Contributor / CI ↔ release pipeline | Public GitHub repo, external PRs, GitHub Actions secrets, app-store signing credentials — classic OSS supply-chain boundary. |
| B7 | Generated OpenAPI client/spec ↔ hand-written adapter | The adapter is the only code allowed to depend on generated code (Clean Architecture rule); the spec itself is a trust/versioning boundary. |

## 3. Key data flows

1. **Server profile setup**: user enters, or imports via deep link/QR (see `docs/ARCHITECTURE.md` §"Server profile import" and T8), an OpenCode server address + credential → for imports, a mandatory review screen requires explicit confirmation of the target host before persisting → stored via Keychain/Keystore → used to authenticate OpenAPI/SSE calls.
2. **Real-time session stream**: EventProcessor opens SSE (falls back to polling) → receives session/agent state, chat messages, permission requests, file/diff events → snapshot + reconciliation on reconnect.
3. **Prompt dictation**: user speech → platform speech-to-text API → text → sent to server as a prompt (may contain proprietary code/secrets spoken aloud).
4. **Permission approval**: server emits a tool-call permission request → app surfaces it in-app and/or as a push notification → user approves/denies → decision sent back to server, which then executes (or not) the tool call on the user's machine.
5. **File/diff review**: server streams file contents/diffs → rendered in-app, optionally cached encrypted-at-rest in SQLDelight (see `docs/ARCHITECTURE.md` §"Local cache encryption at rest" and T3) for offline read-only viewing.
6. **Release pipeline**: contributor PR → CI (lint, architecture tests, unit/integration/contract tests, dual-platform build) → maintainer merge to `main` → signed build → TestFlight / Google Play upload.

## 4. Attack surfaces (entry points)

- Network boundary to the OpenCode Server (REST + SSE/polling), on an untrusted or semi-trusted LAN, or over Tailscale.
- Any deep link / QR / URL-scheme handler used to add or update a server profile.
- Push notification action handlers (permission approve/deny from lock screen or notification shade).
- OS speech-to-text integration.
- Local persistence: Keychain/Keystore entries, SQLDelight cache, OS-level app backups, app-switcher snapshots.
- Generated OpenAPI client and the `OpenCodeV2Adapter` boundary.
- GitHub Actions workflows and app-store release signing material.
- Public GitHub repo / external contributor PRs.

## 5. STRIDE risk register

Risk = Likelihood × Impact, rated Low/Medium/High/Critical. Ratings assume the architecture as currently *specified*, before implementation — they should be re-validated once code exists (see §7).

| ID | STRIDE | Threat | Component | Likelihood | Impact | Risk | Mitigation |
|---|---|---|---|---|---|---|---|
| T10 | Tampering / Supply chain | Public OSS repo with a solo maintainer; a malicious/compromising fork PR or Actions workflow config could exfiltrate GitHub Actions secrets or app-store signing credentials, or tamper with a release build. | CI/CD, release pipeline (B6) | Medium | Critical (shipped-app compromise) | **Critical** | Never trigger secret-bearing workflows on `pull_request_target` with untrusted checkout; run fork PR CI under the default `pull_request` event with no secrets; require manual "approve workflow run" for first-time contributors (GitHub default); restrict signing/upload jobs to protected `main`/tag pushes only; prefer OIDC / short-lived tokens over long-lived static store credentials where TestFlight/Play Console support it; branch protection + required reviews already defined in `BOOTSTRAP.md` — verify it's enforced by GitHub settings, not just process. **Detailed mitigation spec, control-by-control status, and acceptance criteria: `docs/CI-CD-SECURITY.md` (OPE-23).** Current status: fork-PR CI (`pull_request`, no secrets) and CD-restricted-to-`main` are already satisfied by `ci.yml`/`cd.yml` (OPE-13); explicit least-privilege `permissions:` and Environment-gated signing are open follow-ups on that pipeline; first-time-contributor approval and branch-protection enforcement can't be verified until the GitHub repo exists (OPE-9) and is configured (OPE-10); OIDC/short-lived signing credentials are a requirement carried into deployment automation (OPE-19), which hasn't been built yet. |
| T1 | Spoofing | User connects to a rogue/impersonating server (malicious AP, ARP/DNS spoofing on shared LAN, or a maliciously imported server profile) that looks like their own OpenCode Server; attacker harvests the auth credential and can present fake session/tool-call data. | App ↔ Server (B1) | Medium | High (credential theft; user may approve attacker-crafted tool calls believing they're their own agent) | **High** | Design finalized in `docs/ARCHITECTURE.md` §"Server identity verification (T1)": trust-on-first-use SPKI fingerprint per server profile (not CA-based pinning, given typical self-signed/plaintext self-hosted deployments); identity verified — pinned match or fresh TOFU acceptance — before the credential is ever sent; fingerprint shown and explicitly confirmed on first connect; any subsequent mismatch fails closed with a blocking, non-dismissible "server identity changed" warning (no silent retry/fallback); plaintext-HTTP profiles get a persistent textual warning, not just an icon. |
| T2 | Spoofing / Tampering | A tool-call permission approval is granted via a notification action without the user actually reviewing the command/diff (notification spoofing, Android overlay/tapjacking, lock-screen quick actions, accidental tap). | Notification permission approval (B4) | Medium | High (arbitrary tool execution on the user's dev machine) | **High** | Design finalized in `docs/ARCHITECTURE.md` §"Permission approval confirmation (foreground + authenticated)": notifications carry no inline "Approve" action (only "Deny," which is safe/reversible and needs no extra review) and always deep-link into an in-app confirmation screen; approving requires the app in the foreground, full command/diff disclosure, a distinct explicit confirmation tap, and a mandatory biometric (or device-credential) re-authentication gate by default; approve/deny is bound to a single-use, content-hashed permission-request ID (ties to T6). |
| T3 | Information Disclosure / Tampering | The local SQLDelight cache holds session transcripts, prompts, and diffs (potentially proprietary code); on a lost/stolen or malware-compromised device these are readable unless the cache is encrypted at rest. | Local cache (B5) | Medium | High | **High** | Design finalized in `docs/ARCHITECTURE.md` §"Local cache encryption at rest": SQLCipher-backed SQLDelight driver on Android (passphrase generated on first run, stored via Keystore); iOS Data Protection (`NSFileProtectionCompleteUnlessOpen`/`.complete`) as the default given the native-linking cost of SQLCipher-for-iOS this early; cache DB and `-wal`/`-shm` files excluded from OS/cloud backups on both platforms; key loss is treated as a cache miss (rebuild from server), never a fatal error. |
| T4 | Information Disclosure | Server auth tokens/credentials leak via verbose logging in the generated OpenAPI client or the `OpenCodeV2Adapter` (e.g., an `Authorization` header or full request/response body logged at INFO/DEBUG). | OpenAPI client / adapter (B7) | Medium | High (bearer token compromise = remote control of the user's dev machine) | **High** | Enforce header/body redaction in the adapter's HTTP logging interceptor; add an automated CI check (not just review) that fails on logging of `Authorization`/token fields or full prompt bodies — the PR policy already lists "secret in logs" as an automatic rejection criterion, back it with a test. |
| T5 | Information Disclosure | Speech-to-text dictation may silently use a cloud STT provider (Apple/Google) on some OS versions/locales, sending spoken prompts (which may contain code or secrets) off-device — contradicting the product's "no code/prompt telemetry" promise. | Speech-to-text (B3) | Medium-High | High (privacy-promise violation, third-party data exposure) | **High** | Design finalized in `docs/adr/on-device-speech-to-text.md` and `docs/ARCHITECTURE.md` §"Speech-to-text dictation and on-device enforcement (T5)": For V1, force on-device recognition APIs where available (`requiresOnDeviceRecognition` on iOS, `SpeechRecognizer.createOnDeviceSpeechRecognizer` on Android); if on-device isn't available for a given locale/OS version, disable dictation with a clear message rather than silently falling back to cloud; disclose actual behavior in the privacy policy. Architecture remains extensible for post-V1 evolution (e.g. server-side Whisper on user's OpenCode server). |
| T8 | Spoofing / Elevation of Privilege | Server profiles can be added via deep link / verified link / QR import; a malicious link or app could otherwise silently add or overwrite a profile pointing at an attacker-controlled server, chaining into T1. | Profile import mechanism (B1) | Medium | High | **High** | Design finalized in `docs/ARCHITECTURE.md` §"Server profile import": prefer verified App Links/Universal Links over a bare custom scheme (anti-hijacking); no bearer credential in the link itself; every import goes through a mandatory in-app review screen that discloses the full target host/fingerprint and requires an explicit, distinct foreground confirmation before persisting; matching an existing profile switches to an explicit "update existing?" comparison — never a silent overwrite; imported profiles get the same first-connect identity verification as manually entered ones (T1). |
| T6 | Tampering / Elevation of Privilege | The EventProcessor's snapshot + reconciliation on reconnect is a prime target if the server is compromised or a MITM occurs: a stale or duplicated permission-approval event could be replayed, or a previously-denied request re-surfaced as pending. The architecture already forbids automatic mutation replay, which is the right baseline. | EventProcessor reconciliation (B1) | Low-Medium | High | **Medium** | Use server-issued, single-use permission-request IDs that cannot be re-approved once decided; add explicit contract/`MockOpenCodeServer` test cases for duplicate, out-of-order, and replayed permission events (the contract-test infrastructure is already planned — extend its scenario list). |
| T12 | Information Disclosure / Tampering (correctness-adjacent) | Offline read-only cache can show stale permission/session state; a user could misjudge a pending action based on data that no longer matches server reality. | Local cache, offline mode | Medium | Medium | **Medium** | Clear, persistent "offline / stale data" UI indicator; disable all mutating actions (including approve/deny) while offline, which the "read-only offline mode" decision already implies — verify it's enforced at the ViewModel/use-case layer, not just hidden in the UI; force reconciliation before re-enabling actions after reconnect. |
| T13 | Information Disclosure | OS task-switcher snapshots can capture sensitive on-screen content (code, diffs, chat) when the app is backgrounded; snapshots may be cached by the OS and can sync to cloud backup. | App lifecycle / OS snapshot (B5) | Medium | Medium | **Medium** | Blank or blur the screen content on background transition on both platforms (Android `FLAG_SECURE` equivalent behavior via Compose, iOS privacy overlay on `scenePhase` change to background). |
| T11 | Tampering | If the OpenAPI spec used to generate the client is fetched or regenerated from an unpinned/remote source rather than vendored, a compromised spec source could alter client behavior. | Generated OpenAPI client (B7) | Low | Medium | **Low-Medium** | Vendor and pin the OpenAPI spec version in-repo; regenerate only through a reviewed PR (already implied by "code généré modifié à la main" being a rejection criterion — extend it to spec provenance); contract tests catch behavioral drift. |
| T7 | Denial of Service | A slow/unresponsive or malicious server, or a MITM, could send unbounded event streams or oversized diffs, exhausting mobile memory/battery. | EventProcessor, diff rendering | Low | Low-Medium | **Low** | Bound message/diff payload sizes with graceful truncation and a "view full file" fallback; enforce a floor on the polling interval; add a memory watchdog around SSE buffering. |
| T9 | Repudiation | No local, tamper-evident record of permission approvals; if disputed, the server (source of truth) is the only log. | Permission approval flow | Low | Low | **Low** | Not a priority given the single-user, self-hosted context — optionally surface the server's own approval history read-only in-app for the user's convenience, not as a security control. |

## 6. Priority summary

- **Critical (1)**: T10 — CI/CD & release-signing supply chain.
- **High (6)**: T1 (server impersonation — design finalized, see `docs/ARCHITECTURE.md`), T2 (notification approval spoofing — design finalized, see `docs/ARCHITECTURE.md`), T3 (local cache encryption — design finalized, see `docs/ARCHITECTURE.md`), T4 (token leakage via logging), T5 (cloud STT privacy leak — design finalized, see `docs/adr/on-device-speech-to-text.md` and `docs/ARCHITECTURE.md`), T8 (deep-link profile injection — design finalized, see `docs/ARCHITECTURE.md`).
- **Medium (3)**: T6 (reconciliation replay), T12 (stale offline state), T13 (app-switcher snapshot leakage).
- **Low (2)**: T7 (DoS via oversized/unbounded stream), T9 (repudiation).

Three of the four **open product decisions** called out in `BOOTSTRAP.md` are now resolved (local cache encryption → T3; server-profile import → T8, folded into the still-open single-vs-multiple-profiles decision; notification-based permission approval → T2, notifications may no longer carry an inline approve action). The remaining one — Liquid Glass vs. pure Compose on iOS — is a UI/platform choice without the same security stakes as the other three.

## 7. Limitations of this initial pass

- Written before `docs/TECH-STACK.md` (OPE-4), `docs/ARCHITECTURE.md` (OPE-5), and any code exist — based entirely on the fixed spec in `BOOTSTRAP.md`. `docs/ARCHITECTURE.md` now exists but is still partial: it covers only the server-profile import mechanism (T8, via OPE-29), permission approval confirmation (T2, via OPE-25), local cache encryption at rest (T3, via OPE-26), server identity verification (T1, via OPE-24), and speech-to-text dictation enforcement (T5, via OPE-28); the rest of the architecture (component structure, data flow, API boundaries, deployment model) remains pending full OPE-5. The concrete SQLCipher/Data-Protection driver wiring for T3, the biometrics/notification `expect`/`actual` wiring plus confirmation-screen UI for T2, and the OkHttp/URLSession fingerprint-pinning wiring for T1, are design-only until the KMP module scaffold (OPE-30), the OpenAPI-generated client (OPE-31), and the design system (OPE-6) exist to implement them against. Other findings may still depend on design details not yet fixed there.
- No dependency/CVE audit performed here — that is the scope of the separate "Perform initial security review" issue (OPE-8), which is currently blocked pending a codebase to review.
- Must be revisited on every subsequent change to network, authentication, or permission-handling code, per standing project policy.
